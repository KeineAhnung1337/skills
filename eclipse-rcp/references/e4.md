# Native e4 parts, model and dependency injection

Identify the `.e4xmi` application model and fragments, part descriptors, commands, handlers, lifecycle classes, services and injected context. Inspect annotations such as `@Inject`, `@PostConstruct`, `@PreDestroy`, `@Focus`, `@Persist`, `@CanExecute`; read the exact annotation/API page before adjusting signatures or lifecycle. Use model IDs and context keys consistently. Never assume an e3 `ViewPart` has the same lifecycle as a native e4 part.

Avoid expensive work in injected constructors or `@PostConstruct` (it can block part rendering). Keep heavyweight model/service computations behind background jobs with cancellation and perform widget changes on the UI thread. Close/dispose event subscriptions, listeners, observables, and SWT resources in the lifecycle appropriate to the instance; understand whether a context or service outlives the part. Avoid holding a part's `Composite` or `IEclipseContext` from a global singleton after the part closes.

Check context ownership and scope before moving work to another thread: injected objects and contexts have lifetimes, and SWT widgets have display-thread affinity. Do not silently replace the e3 compatibility workbench with a pure e4 product to improve startup: this affects extension points, menus, handlers, perspectives and persisted state.

Local references: `reference/api/org/eclipse/e4/ui/model/application/`, `reference/api/org/eclipse/e4/ui/workbench/`, `reference/api/org/eclipse/e4/ui/di/`, `reference/api/org/eclipse/e4/core/contexts/`, `reference/api/org/eclipse/e4/core/di/`. Use exact 4.40 API for available services and annotations; generated model implementation classes under `impl` are not preferred public APIs. The bundled Platform guide has no comprehensive e4 UI model tutorial: `guide/runtime_app_model.htm` describes the **OSGi** application container, not the e4 workbench model. Use the API, local PDE model editor and actual application as authoritative sources.
